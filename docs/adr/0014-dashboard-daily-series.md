# 看板趋势用的逐日序列由各模块单独落盘，并在模块二提供免重跑的刷新入口

驾驶舱的「近 30 天趋势 + 环比箭头」需要**逐日**的 KPI，而当时各模块只落盘聚合值：`transport_kpi.json` 里的 `baseline_all_days` 是一个 90 天的汇总数，撑不起一条折线；模块一也只落盘了六 KPI 的总体值与两个下钻表。

三个候选做法：

1. **看板内实时聚合**：页面每次刷新都重跑一遍基线贪心（约 5 秒）并按窗口聚合。慢，且把 KPI 口径复制进看板层——同一套公式两处实现，迟早对不上。
2. **为补日表而重跑 `transport_optimize.run_all`**：日表确实会产出，但 `run_all` 同时会重跑代表日的 30 秒启发式搜索并覆盖 `transport_kpi.json`。而带时限的搜索**同参数多次求解不保证同解**（实测同一档出现过 876.15 / 870.16 km 两个结果，相差 0.68%），于是 10/11 号票已发表的里程、成本、TCO 结论会被顺带作废——**拿确定性的产物去陪跑一个不确定的搜索**。
3. **各模块各自落盘逐日表，并给模块二一个只算日表的入口**。

我们决定第 3 条：

- 模块一新增 `inventory_accuracy(by="date")` 与 `daily_kpi(tables)`，落盘 `warehouse_kpi/daily_kpi.csv`（库存准确率 / 盘差率 / 收货及时率 / 拣货效率，并带金额列以便窗口内**金额加权**重算）。
- 模块二把 `run_all` 里那段 90 天循环抽成公开的 `daily_baseline_kpis()` + `summarize_all_days()`，落盘 `transport/daily_baseline_kpis.csv`；`run_all` 改为**从日表再聚合**出全量汇总，不再自己跑第二遍循环（两处各算一次正是数字对不上的经典来源）。
- 新增 `python -m src.transport_optimize --daily-only`：只重算并落盘日表，**不碰代表日优化结果**。

## Considered Options

- **看板内实时聚合**：口径会分叉，而且每次刷新都要 5 秒计算。
- **重跑 `run_all` 顺带产出日表**：省一个入口，但会把已发表的优化结果换成一个新的随机落点，连带 TCO 与台账全部失配。
- **让驾驶舱只显示能由现有产物直接算出的指标**：能凑出满载率（车日表）与异常率，但时间窗达成率与单均成本的日序列无源可取——趋势线会缺掉 KPI 卡片里的两个核心指标，等于没做。

## Consequences

- 「一键复现」的脚本顺序不变（`transport_optimize` → `transport_decisions`），日表随主流程一并产出；只想刷新日表时可以走 `--daily-only`，秒级完成且不动其他产物。
- 全量汇总与逐日表**同源**：`summarize_all_days(daily)` 与已发表的 `baseline_all_days` 逐字段相等，有一条**读盘核对**的测试守着（见下）。
- **逐日值落盘时不取整。** 这是实现期被评审量出来的坑：日表原先把每天的距离与成本各自
  `round(2)` 再求和，而旧的全量循环是整体求和后取整——两者差 **0.1 km / 0.06 元**，重构反而
  制造了 ADR-0013 明令禁止的「两处数字对不上」。舍入只应在**发布口径**（汇总）那一步做一次。
- 与其配套的教训是**测试不能自比**：最初的守护测试在同一份内存对象上比较
  `summarize_all_days(daily)` 与 `kpi["baseline_all_days"]`，两边都出自同一次 `run_all`，
  是循环论证，抓不到上面那 0.1 km。现已改为读**磁盘上已发表的** `transport_kpi.json`
  与 `daily_baseline_kpis.csv` 对账，重新分叉即失败。
- 看板层因此**不含任何 KPI 计算公式**，只做窗口聚合（先求和再相除，不取逐日平均）——该层是纯函数、可单测。
- 代表日的优化结果仍然只在重跑 `run_all` 时更新，届时 10/11 号票的文档与台账须同步重取（该纪律已写入 ADR-0013）。

---

> **2026-09-15 后记：上面第 2 条候选的反对理由已被推翻，决定保留。**
>
> 「带时限的搜索**同参数多次求解不保证同解**」是错的。OR-Tools 的 routing 搜索**没有随机源**
> （参数表里没有 `random_seed`），唯一的不确定性是 `time_limit` 这个**墙钟**；把停止条件换成
> 解数（`solution_limit`）之后，代表日的重跑**逐字段复现**，含 CPU 被占满时。所以 876.15 与
> 870.16 **不是「两个随机落点」**，而是一个正确结果与一个被负载挤掉迭代的结果。见 ADR-0015。
>
> 因此第 2 条候选「重跑 `run_all` 顺带产出日表」**不再会作废已发表结论**——数字不会移动了。
> 但我们**仍选第 3 条**：`--daily-only` 秒级完成、职责单一（只算日表就不碰别的产物）。
> 「重跑反正没风险」不构成顺手重跑的理由。原文保留，以存当时的判断。
>
> 本 ADR 末条（重跑时文档与台账须同步重取）仍然成立，且现在更有底气——重跑确实不会移动数字。
