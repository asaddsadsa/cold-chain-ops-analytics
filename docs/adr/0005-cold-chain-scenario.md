# 成都场景设定为冷链城配，Olist 分布仅作形状借用

3.4 强制要求车厢温度围绕 [2,8℃] 监控、计算温控达标率并埋「温控波动」异常，但订单重量 / 体积从 Olist（巴西综合电商，非冷链）的真实分布抽样。两者语义必须对齐，否则温控 KPI 无所依附；而删掉温控又违反范围锁定。

我们决定：**成都场景整体设定为冷链城配 DC**（生鲜 / 医药最后一公里，服务超市 / 便利店 / 驿站 POI），温控 KPI 与埋点完全成立。Olist 的重量 / 体积**仅作为「典型订单多重多大」的分布形状来源**借用。数据分类上：成都配送订单表整体登记为**情景假设**（POI 坐标为真实观测、需求量为泊松生成、重量体积分布形状借自 Olist 真实观测），绝不声称这些订单是 Olist 商品或真实冷链观测。

## Considered Options

- 设定为普通电商并去掉温控：删减强制 KPI 与埋点，违反范围锁定。
- 部分车冷链部分常温：无谓复杂化，Olist 分布并不区分冷链 / 常温。

## Consequences

- 台账与报告中，温控达标率、异常率等配送侧数字一律标注「情景假设」类别。
- 这是「四层数据分类」原则的典型示范案例：真实分布（观测）+ 构造过程（假设）= 情景假设，跨数据集借用的性质必须显式声明。
