# VRPTW 节点 = POI：单点一访的需求聚合

配送订单按「每店每日泊松 1–3 单」生成，代表日约 40–180 单散布在 ≤60 个 POI 上。城配的真实物理动作是「一辆车到一个店，把当天该店的货一次卸完」，而不是同一店跑多趟。若节点 = 订单（每单独立到访），既不符物理现实，又把节点数推到 ~180，30 秒时限下求解质量差、地图渲染重叠混乱；若时间窗取交集，交集常为空。

我们决定：**节点 = POI，需求聚合，单点一访**。每个 POI 当日全部订单的重量 / 体积求和为一个需求点；时间窗取各订单窗的外包络 [最早起, 最晚止]；求解器安排单次到访。物理路线层（≤60 节点）与业务 KPI 层解耦：「时间窗达成率」按到访时刻对每张订单**逐单**判定，不丢 3.8 的逐单准时口径。

## Consequences

- 台账登记规则：「同店多单聚合为单次到访、时间窗取外包络、逐单判准时」。
- 看板的优化前 / 后地图、单趟明细均基于聚合后的 POI 节点路线；订单级信息只出现在 KPI 与下钻表中。

## Refinement（2026-09-14，10 号票评审后）

原文的「时间窗取外包络」在实现中被**收紧**为「取覆盖订单数最多的那一刻所属各窗的交集」
（`src/transport_optimize.py::visit_window`）。原因：外包络在数学上可行但**过宽**——
求解器可以合法地把到访停在信封边缘，那一刻几乎没有任何订单真正在窗内，于是
「节点窗被满足」与「逐单达成率」彻底脱钩。10 号票评审实测：外包络下逐单达成率被压到
35%，而同数据下的真实上限是 64%。收紧后的结果**始终是外包络的子区间**，只排除
「满足不了任何订单」的到访时刻，不排除任何能满足全部订单的解，故不违背本条 ADR 的立意
（物理路线层与业务 KPI 层解耦、逐单判定不丢颗粒度），只是把聚合窗从「必要」收紧到「有效」。

配套地，同店各单的时间窗在数据层 D 侧锚定到**门店当日收货波次**（`RECEIVING_WAVE_*`）：
一家店一天只有一波冷链收货窗口。若同店各单的窗各自独立散布在 08:00–18:00，
「单点一访 + 逐单判定」在算术上就不可同时成立，逐单达成率会长期停在个位数倍于
「1/单点平均订单数」的水平，本条的 KPI 层设计随之失效。
