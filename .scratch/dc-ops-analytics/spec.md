# PRD：区域仓配中心运营数据分析与配送路径优化（求职作品集工程）

Status: ready-for-agent

> 本 spec 由 2026-09-13 设计打磨会话（grill-with-docs，16 个决策、10 条 ADR）综合而成。
> 配套约束文档：`CONTEXT.md`（术语表，本 spec 全部用语以它为准）、`docs/adr/0001–0010`、`data_sources_ledger.md`（台账草稿）、`docs/implementation-plan.md`（阶段门禁拆解）。
> 原始需求：《仓配项目-Agent构建提示词.md》（功能范围以其 3.1–3.12 为准，不得删减；本 spec 与其冲突处以 ADR 为准并已在下文标注）。

## Problem Statement

求职者（物流/供应链运营方向）需要一个能证明「数据分析 + 运筹优化 + 工程落地」综合能力的作品集项目。市面常见作品集的痛点：数据全靠编造、结论无法复现、仿真数据被包装成真实观测、算法没有基准验证。招聘方拿到项目后无法一键复现、无法追溯任何一个数字的来源，作品集失去可信度。

## Solution

构建一个「另一个人拿到后可以从零一键复现全部结果」的完整工程：以真实电商订单（Olist）、真实地理路网（高德）、学术标准算例（Solomon）、仓内过程仿真（SimPy）四类数据为底座，模拟某区域冷链城配中心连续 90 天的仓储与配送运营，走通「多源数据获取与生成 → 仓储运营分析 → 仓内作业仿真对照 → 运输调度优化 → Streamlit 看板 → PDCA 改善报告 → 部署与复现整理」全链路。最高原则是**数据四层分类**（真实观测 / 学术基准 / 过程仿真 / 情景假设）：每个数字都能在《数据来源与参数标定台账》中追溯到来源与性质，禁止把仿真/假设表述为真实观测。

## User Stories

### 数据可信与溯源

1. 作为招聘方，我想让报告与看板中的每个数字都能追溯到台账，以便判断候选人的结论是否可信而非编造。
2. 作为招聘方，我想看到每个数据集/参数被明确标注四类性质之一（真实观测/学术基准/过程仿真/情景假设），以便区分哪些是真实业务证据、哪些是构造情景。
3. 作为求职者，我想把所有假设参数（拣货秒数、车辆成本、异常概率等）登记台账并附低/中/高三档敏感性分析，以便面试被追问时能展示取值理由与稳健性。
4. 作为复现者，我想在无网络、无高德密钥的干净环境中凭仓库预置缓存复现全部分析与看板，以便验证「一键复现」承诺。
5. 作为复现者，我想让所有随机种子按数据层独立具名并集中声明，以便单独重跑某一层数据而不污染其他层。
6. 作为安全审计者，我想让高德密钥只从环境变量/.env 读取、提交前全局扫描防泄露、.gitignore 排除 .env 与原始大文件，以便确认无密钥外泄风险。

### 数据层 A：仓内运营仿真

7. 作为数据工程师，我想生成连续 90 天的仿真仓（SKU 500、库位 800、日均出库 200–400 单，五张表），以便为仓储分析提供口径自洽的底座。
8. 作为数据工程师，我想让表间外键与时间逻辑自洽（拣货完成晚于开始、复核晚于拣货、出库晚于复核、到货偏差可控），以便 KPI 计算不出现负时长。
9. 作为分析师，我想在数据中主动埋入四类问题（A 类 SKU 远库位、P03 高盘差、14–16 点拣货效率低谷、收货可控晚到），以便分析代码能定量复现每个埋点、证明「数据→诊断→改善」闭环真实存在。
10. 作为分析师，我想在数据生成后自动输出质检摘要（各表行数、时间范围、每个埋点的统计验证值），以便门禁判断埋点是否成立。

### 数据层 B：Olist 真实订单

11. 作为数据工程师，我想实现「本地检测→kagglehub 自动下载→失败报错并给手动放置指引」三段式获取（仓库已预置九表到本地 raw 目录），以便复现者有无 Kaggle 凭证都能拿到数据，且严禁编造数据替代。
12. 作为数据工程师，我想按既定规则清洗（时间字段转 datetime、剔除非 delivered、剔除时间矛盾、邮编多坐标按众数/均值聚合），并输出清洗前后行数对比与剔除原因统计，以便清洗损耗可解释。
13. 作为分析师，我想从 products 表拟合商品重量/体积经验分布并保存，以便配送情景（数据层 D）以真实分布形状抽样。
14. 作为分析师，我想统计 Olist 真实延迟率（实际送达晚于预计送达的占比），以便作为在途异常概率的标定基准并写入台账。

### 数据层 C：成都真实地理

15. 作为数据工程师，我想把虚拟 DC 设在成都青白江物流聚集区（坐标经高德地理编码获取，失败用青白江城区坐标并登记），以便场景贴合真实物流地理。
16. 作为数据工程师，我想分页抓取成都主城区与青白江的超市/便利店/驿站 POI 40–60 个（限速 ≥0.3s、按行政区控制空间分散度、缓存后不重复请求），以便配送点真实且分布合理。
17. 作为数据工程师，我想用高德距离测量批量接口构建「DC+全部 POI」61×61 对称驾车里程/时间矩阵（约 61 次调用、指数退避重试、永久缓存），以便下游优化用真实路网而非直线距离，且配额消耗可控（ADR-0008）。
18. 作为复现者，我想在无密钥时自动降级 OSMnx+networkx 计算矩阵并标记来源为 OSM，以便降级路径也可复现、来源性质不失真。

### 数据层 D：配送情景

19. 作为数据工程师，我想基于 POI 生成 90 天配送订单（每店每日泊松 1–3、重量体积从 Olist 经验分布抽样、时间窗 08:00–18:00 内默认 2 小时、片区 R01–R08 空间聚簇且规则落盘），以便需求情景以真实分布为参数构造。
20. 作为分析师，我想把成都场景设定为冷链城配（车厢 [2,8℃] 监控），以便温控达标率 KPI、温控波动埋点与 POI 类型三者语义自洽（ADR-0005）。
21. 作为成本分析师，我想建立 15 台车（柴油自购/纯电租赁）的车辆表与「两套自营 + 一套外包对标」TCO 成本模型（参数锚点登记台账、来源类别可溯、URL 实现期补齐），以便自营模式选择有真实市场参数支撑（ADR-0009）。
22. 作为成本分析师，我想输出双模式「日总成本=日固定+里程×变动成本」曲线、盈亏平衡里程、司机工资/油价电价/租金三档敏感性、自营优化后单趟成本 vs 货拉拉对照表，以便模式选择建议稳健。
23. 作为数据工程师，我想为每个运单生成在途轨迹（经纬度、时间、车速、车厢温度）与异常表（拥堵/温控波动/晚点/故障/无异常，总体概率以 Olist 真实延迟率标定），并埋入周五晚点偏高、R07 异常偏高、雨日晚点偏高、部分车辆长期低满载四个埋点，以便在途分析有定量靶点。

### 数据层 E：Solomon 算法门禁

24. 作为算法工程师，我想从权威镜像（UMA VRP 库，本机已验证可达；SINTEF 官方为优先源）下载 C101/R101/RC101 算例与 best-known 最优解（禁止凭记忆编造），以便算法验证基准真实可溯。
25. 作为算法工程师，我想用与成都场景完全一致的 OR-Tools 建模（载重+时间窗+车辆数最小化）求解三算例并输出总距离/用车数/耗时/策略/gap%，以便证明建模能力。
26. 作为项目负责人，我想让 gap>10% 成为硬门禁（先排查模型与参数并记录，不得带病进入场景优化），以便优化结果的可信度有算法基准背书。

### 数据层 F：SimPy 仓内仿真

27. 作为仿真工程师，我想实现「订单到达（非齐次泊松，9–11、14–16 双高峰）→拣货（对数正态 ~12s/行）→复核打包（三角分布 30/60/120s）→发货」的离散事件仿真，以便与数据层 A 的效率低谷埋点相互印证。
28. 作为仿真工程师，我想做实验一（ABC 分区存储 vs 原始远库位）与实验二（拣货员 4/5/6 人），各重复 30 次报告均值与 95% 置信区间，输出「时长—人力成本」权衡曲线与拐点，以便库位重排与人力配置建议有统计显著性。
29. 作为仿真工程师，我想把仿真校准锚定自家仿真仓表、与 Olist 仅做无量纲形状对照（变异系数/偏度，出库响应子段），不做跨尺度绝对时长 KS，以便校准诚实可行并在台账声明限制（ADR-0001）。
30. 作为看板开发者，我想预计算各实验档位结果并缓存，以便 what-if 交互瞬时响应。

### 模块一：仓储运营分析

31. 作为分析师，我想按严格口径计算仓内 KPI（库存准确率、收货及时率、拣货效率行/人时、订单平均履约时效、库容利用率、盘点差异率）并分品类/分时段下钻复现 P03 高盘差与 14–16 点低谷两个埋点，以便诊断有定量依据。
32. 作为分析师，我想按严格口径计算 Olist 真实履约 KPI（履约总时长/出库响应/在途时长、真实准时交付率与延迟率，按州/重量段/月份下钻，与 reviews 交叉），以便展示真实数据分析能力。
33. 作为分析师，我想按**仿真仓出库行数**做 ABC 分类（70/20/10，阈值可调，输出帕累托与 A 类清单），以便分类与库位体系同源、能直接驱动重排（ADR-0002）。
34. 作为分析师，我想建立「库位—拣货台」距离模型，以 Σ(出库频次×距离) 量化 A 类 SKU 重排前后的行走成本与预计拣货效率变化，并与仿真实验一互相印证，以便库位优化建议双重验证。
36. 作为开发者，我想让每个 KPI 函数可独立调用并配单元测试（每个 KPI 至少一个正例），以便口径回归有保障。

### 模块二：运输调度与在途分析

37. 作为调度分析师，我想按严格口径计算运输 KPI（时间窗达成率、满载率均值与分布、柴油/纯电双模式单均运输成本、里程利用率、异常率、平均异常处理时长、温控达标率）并全部落盘，以便运输诊断可复现。
38. 作为调度分析师，我想让 VRPTW 节点=POI：同店当日多单做**需求聚合**（重量体积求和、时间窗取外包络、单点一访），到访后按每张订单各自的窗**逐单**判定时间窗达成率，以便路线贴合城配物理现实且 KPI 不丢单据粒度（ADR-0004）。
39. 作为调度分析师，我想在**代表日**（90 天中订单量最大工作日）做完整「基线贪心 vs OR-Tools 优化」精算（30s 上限、目标=固定+里程成本、出两套 GeoJSON），其余 89 天用贪心覆盖全量，按代表日单均节省率外推月/年金额（外推假设登记台账），以便「一键复现」时长可控且金额换算有真实分母（ADR-0003）。
40. 作为调度分析师，我想输出优化前后对比表（总里程/用车数/总成本/准时率及各项降幅%）与「单趟节省→月度/年度金额」换算过程，以便收益可追溯。
41. 作为调度分析师，我想按周输出异常类型分布与典型案例清单，复现周五与 R07 高异常埋点，以便「周度异常复盘」机制有数据支撑。
42. 作为成本分析师，我想基于真实成本参数计算双模式优化前后日/月总成本、盈亏平衡里程、自营 vs 货拉拉对照与三档敏感性，输出模式选择建议，以便车队投资决策完整。

### 模块三：Streamlit 看板

43. 作为看板用户，我想在运营驾驶舱看到 KPI 卡片（库存准确率、**时间窗达成率**、满载率、单均成本，带环比箭头）、近 30 天趋势折线与最新异常预警清单，以便一屏掌握运营状态（卡片指标用「时间窗达成率」而非「真实准时交付率」，见 CONTEXT.md 术语拆分）。
44. 作为看板用户，我想在仓储分析页看到 ABC 帕累托、分时段拣货效率柱状图（可见 14–16 点低谷）、800 库位热力图、盘差 Top10 品类表（P03 居前）、Olist 履约分布与延迟下钻、仿真实验结果（拣货员人数滑块切 4/5/6 档），以便仓储诊断可视化。
45. 作为看板用户，我想在运输分析页用 Folium 真实地图切换「优化前/优化后」路线并显示各点时间窗，看到里程/用车/成本对比、满载率分布、异常饼图+周趋势、温控仪表、双模式 TCO 曲线（标注盈亏平衡里程）与外包对照表，以便运输成果一图讲清。
46. 作为看板用户，我想在改善建议页看到「问题诊断→改善动作→预期收益」表（条目自动汇总、数字引用结果文件），并用 what-if 控件调车辆数 5–20（读 16 档预计算缓存，ADR-0010）、ABC 阈值、拣货员人数、动力模式与三档敏感性，控件变化 KPI 瞬时重算无报错，以便交互式验证改善逻辑。
47. 作为看板用户，我想用侧边栏全局筛选器（日期范围、品类、配送区域）作用于全页，所有图表中文标题/坐标轴/单位、悬停明细、统一配色、读数统一缓存，以便体验专业流畅。

### 模块四：PDCA 报告与交付

48. 作为招聘方，我想读一份 P（3–5 个有数据支撑的问题，各注数据类别）→D（库位重排、VRPTW 优化、周度异常复盘、人力配置）→C（每个数字引用程序输出文件，禁止编造）→A（SOP 与看板常态化监控）结构的改善报告，以便看到完整的改善方法论闭环。
49. 作为招聘方，我想同时拿到 Markdown 与 PDF 两版报告（PDF 经 headless Edge 生成、已实测中文渲染通过；环境不支持时降级交付 Markdown 并在 README 写明转换步骤、显式告知，不得伪装已生成，ADR-0007），以便阅读与存档。
50. 作为复现者，我想按 README「装依赖→备数据→跑数据层→算指标→启看板」五步从零复现，并看到 Streamlit Community Cloud 部署说明（含 st.secrets 配置），以便验证工程可复现性。
51. 作为项目维护者，我想让台账持续维护（每个数据/参数的取值、类别、来源 URL、日期、口径备注，假设参数附敏感性结论），以便简历与报告可用的每个数字都能追溯。

## Implementation Decisions

（完整理由见对应 ADR，此处为约束摘要）

- **范围锁定**：只实现原始需求 3.1–3.12，不新增、不删减任何 KPI、埋点、图表、报告章节；偏离需求的新想法入 backlog 经用户确认。
- **技术栈**：Python 3.14.6（已验证全栈 cp314 wheel）；pandas 锁 2.3.3（不用 3.0，规避 CoW 破坏性变更，ADR-0006）；SimPy、OR-Tools 9.15、requests、Faker（仅姓名/车牌等无关结论文本）；Streamlit + Plotly + Folium（原列的 streamlit-echarts 因与 streamlit 1.63 运行时不兼容已移除，图表统一用 Plotly，见 ADR-0011）；存储只用 CSV/SQLite；requirements.txt 锁全版本。
- **种子体系**：每数据层独立具名种子，集中于统一 config 模块声明；仿真实验由基础种子派生 30 个子种子（Q4 决策）。
- **数据获取**：Olist 九表已预置本仓库，拷入 raw 目录走「本地已存在」分支，三段式获取逻辑保留（Q3）；高德密钥仅环境变量；外部 API 结果一律永久缓存，无密钥无网络可复现。
- **高德矩阵**：距离测量批量接口按目的地逐列请求（约 61 次调用）+永久缓存；限速、指数退避 1/2/4s×3；无密钥降级 OSMnx 并标记来源（ADR-0008）；配额数字实现期登录控制台核实入台账。
- **场景设定**：成都青白江冷链城配 DC；配送订单表整体归类情景假设（POI 坐标真实观测、需求泊松生成、重量体积分布形状借自 Olist）（ADR-0005）。
- **ABC 分类**：基于仿真仓出库行数，不属于 Olist 侧；Olist 只算真实履约 KPI（ADR-0002）。
- **准时率术语**：Olist 侧叫「真实准时交付率」，配送侧叫「时间窗达成率」，驾驶舱卡片显示后者（CONTEXT.md）。
- **VRPTW 结构**：节点=POI、需求聚合、单点一访、逐单判时间窗达成率（ADR-0004）；代表日精算+贪心全量+节省率外推（ADR-0003）；与 Solomon 验证同构建模；gap>10% 硬门禁。
- **仿真校准**：锚定自家仿真仓表；与 Olist 只做无量纲形状对照，不做绝对时长 KS；限制写入台账（ADR-0001）。
- **成本模型**：参数以需求文档 2026-09 市场检索值为中位锚点，台账登记来源类别+「URL 待补」标记，全部归情景假设并做三档敏感性（ADR-0009）；禁止编造 URL。
- **what-if 性能**：车辆数 5–20 共 16 档离线预计算缓存，滑块只切档；仿真实验档位同样预计算（ADR-0010）。
- **PDF**：headless Edge `--print-to-pdf`（本机实测通过，中文字体用系统微软雅黑/黑体）；检测不到浏览器时降级 Markdown+README 转换指引并显式告知（ADR-0007）。
- **工程结构**：遵循需求 3.12 的目录树（data/{raw,warehouse,geo,delivery,processed}、src 九脚本、app.py+pages、report、tests、台账、.env.example、.gitignore、requirements.txt、README）。
- **工作纪律**：阶段门禁推进（骨架→数据层→模块一→模块二(过 Solomon 门禁)→看板→报告→部署），每阶段自测通过才进入下一阶段；失败不伪装、阻塞显式说明；函数 docstring+关键步骤中文注释。

## Testing Decisions

**好测试的标准**：只测外部行为（输入数据→输出数值/文件），不测实现细节。本项目的「行为」有两类：KPI 函数的口径正确性、数据生成器的埋点可复现性。

**测试缝（seams）**——全部利用需求已规定的高位缝隙，不新增：

1. **KPI 纯函数缝（主缝）**：仓储/运输全部 KPI 计算函数可独立调用（需求 3.7 已规定），pytest 对每个 KPI 至少一个正例：手工构造小规模输入 DataFrame，断言输出等于手算期望值。覆盖严格口径（库存准确率金额加权、收货及时率 30 分钟容差、拣货效率行/人时、时间窗达成率逐单判定、满载率、温控达标率、ABC 阈值边界）。
2. **数据产物缝（埋点回归）**：每个数据生成脚本的质检摘要是落盘产物；测试读取质检文件断言埋点统计量成立（P03 盘差率显著高于其他品类、14–16 点秒/行显著高于其余时段、周五晚点率偏高、R07 异常率偏高、矩阵对称完整、时间逻辑无违例）。固定种子下产物字节级可复现本身也是断言。
3. **算法门禁缝**：Solomon 三算例的 gap% 输出对 best-known（从权威源下载，不硬编码在测试里）断言 ≤10%；解析器对手工构造的小算例文本断言字段解析正确。
4. **成本模型缝**：TCO 函数（日总成本、盈亏平衡里程、敏感性档位）是纯函数，对手工算例断言；与 Excel 校验工作簿的三指标交叉一致。

不测：Streamlit 页面渲染（以「4 页打开无报错+交互手测清单」验收，写入 README 验收步骤）；外部 API 实时行为（以缓存产物为测试输入）。

**Prior art**：本仓库为新建工程，无既有测试；tests/ 目录结构按 pytest 惯例（每模块一个测试文件，与被测脚本同名对应）。

## Out of Scope

- 真实企业数据接入（项目为教学模拟，DC/车队均为虚拟设定）。
- MySQL/Redis 等外部数据库服务（需求明令禁止）。
- 付费地图服务（仅 Folium 本地渲染 + 高德免费 Web 服务 API + OSM 降级）。
- 实时求解的 what-if（一律预计算缓存切档）。
- Olist 侧的 ABC 分类（ABC 只属于仿真仓体系）。
- 跨尺度绝对时长 KS 校准（已以形状对照替代并声明限制）。
- 隐私数据采集；Faker 仅用于姓名/车牌等无关结论文本。
- 本会话不写工程代码（Q1 决策：设计打磨会话，实现另行启动）。

## Acceptance Criteria（DoD）

1. 仓内 5 张表+配送/车辆/在途表全部生成，质检摘要中 **6 类埋点**（A 类远库位、P03 高盘差、14–16 点低谷、收货晚到、周五/R07/雨天/低满载）均可被分析代码定量复现。
2. Olist 九表清洗完成，真实履约 KPI 与重量/延迟分布统计输出完整，清洗损耗可解释；真实延迟率作为异常标定基准写入台账。
3. POI 40–60 个且空间分布合理；61×61 真实路网矩阵完整对称；无密钥环境凭缓存或 OSM 路径可复现。
4. Solomon 三算例求解结果与 gap 记录在案，**gap≤10% 门禁通过**；best-known 来自下载的权威源（非凭记忆）。
5. SimPy 两组对照实验各 30 次重复、输出 95% CI；与 Olist 的形状对照结果与跨尺度限制声明落盘。
6. 仓储、运输全部 KPI 计算完成且口径与需求逐条一致；库位重排与 VRPTW 均有前后量化对比；月/年金额换算过程可追溯（外推假设登记台账）。
7. 双模式 TCO 对比、盈亏平衡里程、自营 vs 货拉拉对照、三档敏感性全部输出；车辆参数台账含来源类别与锚点值，URL 待补项显式标记 🔶（不伪装已溯源）。
8. 4 个看板页面正常打开，全局筛选、优化前后地图切换、全部 what-if 控件生效且无报错、滑块瞬时响应。
9. PDCA 报告结构完整，每个数字能在 processed 结果文件中找到对应；Markdown+PDF 两版（或降级时显式告知）。
10. 单元测试全绿（每个 KPI 至少一个正例+埋点回归+门禁断言）；按 README 五步在干净环境一键复现；Streamlit Community Cloud 部署步骤（含 st.secrets）写明；全局扫描无密钥泄露。
11. 台账无未解释的 🔶 残留（或每项显式标注阻塞原因与补救路径）。
