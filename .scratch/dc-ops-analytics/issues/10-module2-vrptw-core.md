#### 时间窗达成率：从 35%（无意义）修到 79.55%（可用 KPI）

评审在上一版实现上实测出逐单达成率只有 35%，且基线与优化几乎持平。我当时把它归因为
「ADR-0004 单点一访的算术硬顶 = 1/单点平均订单数 = 36.6%」——**这个前提是错的**：
44 个点里有 25 个点的当日各单窗口完全重叠，真实上限是 64.2%。差距的成因是另外两条，
本票已连同数据层 D 一起修掉：

**修法一（数据层 D）：门店当日收货波次。** 一家店一天只有一波冷链收货窗口，原实现却给同店
各单**独立**抽窗（可一个上午 8 点半、一个下午 3 点），一次到访不可能同时满足。改为每店每日抽
一个波次起点（08:30–15:00），该店当日所有订单的窗锚在这一波上、只加 0–10 分钟抖动。
实测 2638 个多单店日 **100%** 存在公共交集。这是「单点一访 + 逐单判定」能同时成立的**前提**。

**修法二（本票）：节点窗从「外包络」收紧为「最优点访窗」。** ADR-0004 原文写「时间窗取外包络」，
外包络在数学上可行但**过宽**——求解器可以合法地把到访停在信封边缘，那一刻几乎没有任何订单
真正在窗内，于是「节点窗被满足」与「逐单达成率」彻底脱钩。改为 `visit_window`：扫描线找覆盖
订单数最多的那一刻，取「包含它的那些窗」的交集。结果**始终是外包络的子区间**，只排除
「满足不了任何订单」的到访时刻，不排除任何能满足全部订单的解。已作为 Refinement 追加进 ADR-0004。

**修法三：让 KPI 量的是「实际」而不是「计划」。** 到达时刻叠加数据层 D 异常表的在途延误，
数据层 D 的在途异常这才真正接进运输 KPI。延误挂在**配送点**上而非「趟」上——节点所辖订单对
两套方案完全相同，因此两套方案面对同一份延误，比较才只反映排程差异。早先按「趟」取最大延误
会系统性惩罚并载更多的优化方案（一辆车装 5 单自然比装 3 单更容易撞上严重异常），
那是耦合方式造成的假象，不是排程质量。

**修法四：给目标函数补上抗延误余量。** 只做前三步时，优化方案的时间窗达成率**反而低于**朴素
贪心（15.2% vs 34.1%）——纯成本目标把「早到等待」当纯浪费，排出的计划没有余量吸收延误。
补了两项：① 计划窗止减去 `TRANSPORT_DELAY_BUFFER_MIN = 30` 分钟的延误缓冲；
② OR-Tools 时间维加**软上界误点惩罚**（300 元/分钟）。这里踩了一个坑并靠实测纠正：
软上界最初设在**窗止**上完全无效——硬约束本来就禁止越过窗止，惩罚永远不会触发，数字纹丝不动；
必须设在**窗起**才能逼出「贴窗起到达」，把「窗起→窗止」整段余量留给延误消耗。

**结果**：逐单达成率 79.55%（实际口径，含在途延误），45/45 个配送点的当日各单窗可由一次到访全部满足，
理论上限 100%。基线与优化**同为 79.55%**——这是真实结果而非巧合：两套方案都排在窗内，
延误把同样那批点推出窗；优化的收益体现在里程与成本（−25.12% / −13.12%）而非准时。
把这个结论如实写出，比硬造一个「优化让准时率提升 x%」的数字诚实得多。

#### 口径与实现要点

- **建模与 05 号票同构**：同样 `PARALLEL_CHEAPEST_INSERTION` 首解 + `GUIDED_LOCAL_SEARCH`、同样「固定成本 >> 里程成本」实现车辆数优先、同样 `slack_max = horizon` 允许早到等待（05 号票踩过的两个坑直接复用结论）。差别只有两个容量维度（重量 kg / 容积 L）与时间单位为秒。
- **规模与单位**：距离用米、时间用秒、容积用升序，全部整数化后交给 OR-Tools（弧权必须为整数）。
- **未服务点必须显性**：基线贪心在「剩余点任何车都装不下/送不到」时收车退出，避免死循环；`time_window_achievement` 把未服务单单独计数（`n_unserved`），不混进达成率的分母叙事里。
- **约束经独立断言复核**：单测逐趟校验载重 ≤ 额定、容积 ≤ 额定、每个到访时刻 ≤ 该点窗外包络，以及「每个被服务点恰好访问一次」。

### 代码评审批次（2026-09-14，Standards + Spec 双轴）

评审提出并经核实的六条，已全部修复：

1. **时间窗上限的归因是错的（最严重）**：见上文——把「目标函数不含准时项」误判成「聚合规则不可逾越」，还给出了 36.6% 这个错误的「硬顶」。已改为实测上限 64.2%（`optimal_single_visit_ceiling` 落盘）+ 如实陈述 28.3pp 的差距来自目标函数缺项。
2. **全量 90 天只算了里程/车次/单数**：票据明写要「总里程/用车数/**总成本/时间窗达成率**」，ADR-0003 也要求用全量口径当**真实分母**。已补齐：全量柴油成本 332,065 元、纯电 301,504 元、逐单达成率 42.79%（这三个数在时间窗修复与数据层 D 重跑后更新为 424,589 / 387,482 / 86.49%，见台账）。
3. **未服务单被虚报为「已覆盖」**：`n_orders += len(grp)` 无条件累加全部订单，而贪心在 58/90 天里共跳过 271 单。已拆成 `n_orders_total / n_orders_served / n_orders_unserved`，并加 `logger.warning` 与 `served_node_indices` 辅助函数；报告标题里也不再写「均已覆盖」。
4. **基线贪心的 `max_route_min` 形同虚设**：可行性判断用**原始到达时刻**算回程，漏掉了早到等待；实测可超限 49%（真实数据未触发，因最长 599.7 分钟恰好卡在 600 以内——潜伏缺陷）。已改用实际开始服务时刻。
5. **外推公式与 config 文字不符**：config 写「单车单趟平均节省 × 月配送天数 × **车队规模**」，代码实为「单均节省 × 当日单数 × 天数」。已把 config 文字改成与实现一致（单均口径），避免两处金额不可互证。
