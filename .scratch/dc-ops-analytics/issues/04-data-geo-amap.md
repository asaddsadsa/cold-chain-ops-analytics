**⚠️ 纠正 2026-09-13 的错误诊断**：当时判「高德 key 级权限/配额受限、OSMnx 也不可用」并据此把本票标 needs-info 请用户换 key——**这个结论是错的，让用户白跑一趟，特此纠正**。两个真实根因均与 key 无关：
1. **探测手段缺陷**：用 `curl --data-urlencode` 传中文关键词（肯德基/超市），Windows Git Bash 下编码被打乱，高德收到乱码 → 合法返回 status=1/infocode=10000/count=0。这不是 key 受限（key 一直可用，用户给的就是环境变量里那个）。改用 Python urllib（正确 UTF-8）后同样请求 count=569。
2. **POI 抓取设计 bug**：`search_district_pois` 原把 `city` 硬编码为「成都」全市搜索后按 adname 事后过滤——高德按相关性排序，远郊青白江在全市前几页排不上（全市结果里青白江仅 2 条）；且「高新区」不是合法 adname、citylimit 对其失效 → 抓 0 个，总数仅 32。改为**按区直接检索 `city=区名`** 后，青白江得 14 条、郫都区（替换非法的高新区）得 5 条，总数 49 达标。
3. **附带加固**：实测高德个人 key 在 0.3s 限速下仍偶发 QPS 超限（infocode 10019/10021）。原 `amap_get` 只对网络异常退避、对业务错误直接返回；矩阵构建发 ~50 次请求时此缺陷会导致整列缺失。已加固为对 QPS/引擎瞬时错误码一并退避重试，并补 3 个回归测试。本次矩阵构建实测命中 3 次 QPS 超限，全部被兜住。

**OSMnx 降级**：Overpass API 在本机网络确不可达（ConnectionReset），但既然 key 可用、走 amap 主路径，降级路径未被触发；代码保留，供他人无密钥时兜底。

**验证**：全量测试 101+ passed；`python -m src.geo_poi` + `python -m src.geo_matrix` 端到端跑通；缓存命中零请求实测通过。
